# MonoMod hook canary — 0.3.2 (build 9)

This physical test checks the hook machinery needed to host Everest. It keeps
build 6's proven Mono 8.0.28 JIT, alias allocation algorithm, native import resolver and worker detach
fix. It uses two 16 MiB preparation arenas. The new pieces are pinned MonoMod,
an explicit iOS memory backend and actual Hook/ILHook fixtures. This app does
not contain Celeste, Everest, game mods or game assets.

Build 8 passed all eight managed stages and 21 hook assertions, then exhausted
its 8 MiB code budget while compiling a generated struct hook. Build 9 raises
the budget to 32 MiB and records memory usage at hook stages. The runtime,
MonoMod and test DLL are unchanged. Its own script now prepares two 16 MiB
arenas. Your setup was correct. Import the included DLL and let this app send
its fresh script; do not reuse a script from an older build.

## Files and setup

Open **Files → iCloud Drive → Celeste JIT Tests → 0.3.2-build-9** and download:

- `CelesteJITHooks-v0.3.2-build-9-unsigned.ipa`
- `HookCanary-v0.3.0.dll` — the external IL test assembly, compiled after the IPA.

The folder also contains `README-FIRST.txt`, this guide, checksums and an empty
`Results` directory. The exact session script is generated by the running app.
The separate `celeste-jit-probe-TEMPLATE.js` is reference material; it lacks the
fresh PID, addresses and nonce and cannot be run by itself.

1. Fully close the old canary process. Update it in **LiveContainer 1**, keeping
   its data and old diagnostics. Build 9 uses the same canary bundle ID and
   is still named **Celeste Hook Canary**. Keep **Launch with
   JIT OFF** and **JIT Launch Script empty**, as in your successful build 6
   setup. Retain the file-picker fix if you enabled it previously.
2. Prepare **StikDebug in LiveContainer 2** with its usual connection/VPN. Open
   Celeste Hook Canary in LiveContainer 1. No Xcode debugger is needed.
3. Tap **1. Import HookCanary DLL** and select `HookCanary-v0.3.0.dll`.
   The button should become **Test DLL imported ✓**. The earlier `Canary-v0.2.2.dll` does not include the hook entry points;
   use the supplied `HookCanary-v0.3.0.dll`.
4. Tap **2. Enable via LiveContainer 2**, complete the StikDebug request, then
   return to the existing canary in slot 1. It prepares 2,048 pages and runs native
   checks automatically after verified detach. Keep that same process alive.
5. At **NATIVE PASS · READY FOR MONO**, tap **3. Run hook tests**; scroll if needed.
   Keep the app in the foreground. Allow up to two minutes because all JIT and
   hook stages are logged to disk.
6. At **HOOKS PASS · BACKGROUND NEXT**, wait **10 seconds** in the foreground.
   Go to the Home Screen for **at least 20 seconds**; 30 seconds is fine. Return
   to the same running canary without closing it or requesting JIT again.
7. At **READY · RUN RESUME TESTS**, tap **4. Run resume tests**. The button stays
   disabled until the app records a background interval of at least 20 seconds
   after the first phase. If the interval was too short, go Home for 30 seconds
   and return again.
8. At **PASS · HOOKS + RESUME**, wait **10 seconds**, then tap **Export diagnostics**.
   Choose **Save to Files → iCloud Drive → Celeste JIT Tests → 0.3.2-build-9 →
   Results**. Tell me when it is saved so I can inspect it. Export on failure
   as well. Update the recorded LC/StikDebug versions if they changed from
   3.8.9 / 3.1.9.

Target: iPhone 15 Pro Max, iOS 26.5, canary in slot 1, StikDebug in slot 2.

## What the result means

The first phase reruns the eight managed JIT checks, then exercises original
calls, altered arguments, disposal/undo/reapply, configured hook ordering,
IL changes, combined Hook/ILHook chains, instance and struct ABIs, exceptions,
GC and 64 calls from a managed worker. One Hook and one ILHook remain installed.

The second phase attaches another native worker to the existing Mono domain.
It executes those retained hooks after the real background interval, runs GC,
removes the hooks, compiles a new DynamicMethod, and installs/removes fresh
Hook and ILHook instances. The final status requires both phases and clean
worker detachment. The logs additionally verify JIT addresses and patch writes
inside the prepared aliases. Exported evidence still needs review before G2
is accepted; this is not a mod compatibility or gameplay result.

The pinned upstream Hook API rejects methods on generic declaring types and
generic source methods. The canary checks that rejection and separately checks
generic execution; it does not claim generic-method hooking support.

## Recovery and manual script fallback

If the app **crashes**, reopen it and immediately **Export diagnostics** before
enabling JIT or running another test. The export includes the previous five
sessions and native console tails. Preserve app data. If it **hangs**, allow
up to two minutes, note the last stage, then close/reopen and export. A stopped
stage or crash is useful evidence; do not repeatedly rerun without saving logs.
If preparation fails, also save StikDebug's script log.

Only if the normal inline route fails: in the current running canary tap
**Export session script (manual setup)**, save that exact `.js`, import it into
StikDebug in LiveContainer 2, then tap **Use imported script in LiveContainer 2**
in the same canary process. Match the PID shown in both apps. Never reuse an
older session script or assign it as a future LiveContainer launch script.

This bounded canary retains a fixed 32 MiB code budget and the Mono domain for
one process lifetime. A second full test requires fully closing and relaunching
it. It has no runtime restart, assembly unload or late memory growth. The AOT
checkout and your earlier test kits are preserved.

If the fixed code budget is exhausted again, the app records an explicit
`jit_code_budget_exhausted` diagnostic and terminates before Mono can use a
null code pointer. Reopen and export as above. It cannot recover that runtime
in place; budget growth/recycling belongs to later game-host work.
